Debugging, DevTools และ Performance

ใช้ breakpoint, Inspector, CPU, memory, network, rebuild diagnostics และ structured logs หา root cause

เวลาอ่าน 76 นาที ระดับ กลาง debug breakpoint DevTools Inspector CPU memory rebuild performance

เป้าหมายของบท

  • debug แบบ reproduce → observe → hypothesize → isolate → verify
  • เลือก Flutter Inspector, debugger, logs, Network, CPU และ Memory ให้ตรงอาการ
  • แยก rebuild, relayout และ repaint ออกจากกัน
  • ปรับ performance หลังมีหลักฐานและเก็บ regression test

Debugging loop

ถ้าขั้น Observe ยังไม่มีหลักฐาน อย่าเริ่มจากล้าง cache หรือเปลี่ยน dependency หลายตัวพร้อมกัน เพราะจะทำให้ไม่รู้ว่าสาเหตุจริงคืออะไร

เลือกเครื่องมือจากคำถาม

VS Code debugging

  1. วาง breakpoint ที่ application boundary ไม่ใช่ทุกบรรทัด
  2. ใช้ conditional breakpoint เช่น task.id == 't-42'
  3. ดู Call Stack เพื่อหาผู้เรียก ไม่ดูเฉพาะบรรทัดที่ throw
  4. เพิ่ม Watch สำหรับ state ที่เป็น invariant
  5. Hot restart เมื่อแก้ initialization/global state; hot reload เมื่อแก้ UI body

Structured logs ที่ปลอดภัย

Log context ไม่ log secret
logger.warning(
  'task_load_failed',
  error: failure,
  stackTrace: stackTrace,
  context: {
    'screen': 'task_list',
    'filter': filter.name,
    'requestId': requestId,
  },
);

ห้าม log access token, password, authorization header, full personal payload หรือ secure-storage content แม้อยู่ใน debug build ที่อาจถูกส่งเข้า CI artifact

Build, layout และ paint

Rebuild ไม่เท่ากับ repaint เสมอไป Widget configuration ใหม่อาจทำให้ Element update แต่ RenderObject ไม่ต้อง layout/paint หาก geometry และ visual properties ไม่เปลี่ยน
  • Build: สร้าง configuration subtree ใหม่
  • Layout: คำนวณ size/position ตาม constraints
  • Paint: บันทึก drawing commands
  • Raster: engine แปลง layer เป็น pixel

ลด rebuild อย่างมีเหตุผล

watch เฉพาะ slice ที่ใช้
final pendingCount = ref.watch(
  taskControllerProvider.select(
    (value) => value.valueOrNull?.pendingCount ?? 0,
  ),
);

ใช้ select เมื่อวัดแล้วพบว่า widget กว้างเกินจำเป็นจริง อย่าแยก provider ทุก property จน graph เข้าใจยากเพียงเพื่อหวัง performance

รายการยาว

Lazy list
ListView.builder(
  itemCount: tasks.length,
  itemBuilder: (context, index) {
    final task = tasks[index];
    return TaskTile(
      key: ValueKey(task.id),
      task: task,
    );
  },
)

ใช้ stable key ตาม identity, หลีกเลี่ยง synchronous parsing หนักใน itemBuilder และ paginate เมื่อ dataset ใหญ่จริง

อ่าน frame budget

ที่ 60Hz เฟรมมีเวลาประมาณ 16.7ms; ที่ 120Hz ประมาณ 8.3ms ให้ profile ด้วย mode/device ใกล้ release เพราะ debug instrumentation ทำให้ตัวเลขไม่แทนประสบการณ์จริง

Memory leak ที่พบบ่อย

  • ไม่ dispose controller/subscription/timer ที่ widget เป็นเจ้าของ
  • callback อายุยาวจับ BuildContext หรือ object graph ใหญ่
  • cache ไม่มี eviction policy
  • เก็บภาพ byte ขนาดใหญ่ใน global state

Case study: filter แล้ว UI กระตุก

  1. บันทึก CPU timeline ขณะพิมพ์ค้นหา 20 ตัวอักษร
  2. พบ sort + lowercase ทั้งรายการเกิดทุก keystroke ใน build
  3. ย้าย normalization ไปตอนรับข้อมูล และ derive filtered list ใน controller
  4. debounce เฉพาะ remote search; local list เล็กไม่ต้อง debounce
  5. รัน benchmark flow เดิมและเก็บตัวเลขก่อน/หลัง

ข้อผิดพลาดที่พบบ่อย

  • ใช้ flutter clean เป็นขั้นแรกทุกอาการ
  • จับ exception แล้วทิ้ง stack trace
  • optimize จากความรู้สึกโดยไม่ profile
  • มอง rebuild count อย่างเดียวโดยไม่ดู frame time
  • วัด performance บน simulator/debug mode แล้วสรุป production

Checkpoint ก่อนเดินต่อ

  1. อธิบายหัวข้อนี้ด้วยภาษาของตนเองโดยไม่เปิดคู่มือ
  2. ชี้ไฟล์หรือคำสั่งใน Boilerplate ที่สัมพันธ์กับบทนี้ได้
  3. รันตัวอย่างหรือ verification ที่บทกำหนดและอ่านผลลัพธ์ได้
