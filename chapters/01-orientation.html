01 · เริ่มใช้คู่มือและตั้งเป้าหมายระบบ

A · Orientation & Setup · บทที่ 01

เริ่มใช้คู่มือและตั้งเป้าหมายระบบ

วางเส้นทางจาก Web developer ไปสู่ Flutter developer และรู้ว่าควรอ่านหรือทดลองอย่างไร

เวลาอ่าน 18 นาที ระดับ เริ่มต้น roadmap mental model hot reload capstone

เป้าหมายของบท

  • เข้าใจว่าคู่มือนี้สอนการตัดสินใจ ไม่ใช่เพียง syntax
  • เห็นภาพระบบ Task Management ที่จะสร้างตลอดหลักสูตร
  • วาง workflow อ่าน → ทดลอง → test → อธิบาย → ทำต่อ
  • แยกคำว่า compile-ready, demo-ready และ production-ready
React bridge ถ้าคุณเคยเรียน Next.js จากการสร้าง route, data fetching และ component จริง หลักสูตรนี้ใช้วิธีเดียวกัน แต่เพิ่ม mobile runtime, platform toolchain และ architectural boundary ที่แอปหลาย platform ต้องรับผิดชอบ

ปลายทางที่เราจะสร้าง

completed example เริ่มจาก Boilerplate เดิมที่มี Authentication และ Home แล้วเพิ่ม feature tasks ซึ่งมี list, filter, create, edit, toggle และ delete ทำงานแบบ offline เพื่อให้ clone แล้วรันได้ทันที

เส้นทางหลักเริ่มจาก baseline ที่ทำซ้ำได้ แล้วเพิ่ม language, UI runtime, architecture, feature implementation และ release evidence ตามลำดับ

Learning loop ที่ใช้ทุกบท

  1. Predict: ทำนายผลก่อนรัน เช่น state ไหนจะ rebuild
  2. Run: รัน code, test หรือ command จริง
  3. Observe: อ่าน output, stack trace หรือ UI state
  4. Explain: อธิบายด้วยคำของตนเอง ไม่คัดคำจำกัดความ
  5. Change: เปลี่ยน input หนึ่งอย่างแล้วทำนายใหม่

วงจรนี้สำคัญกับ Flutter เพราะการจำชื่อ Widget ไม่ช่วยวิเคราะห์ constraint, provider lifecycle หรือ route redirect เมื่อระบบจริงซับซ้อนขึ้น

สามระดับความพร้อม

ระดับพิสูจน์แล้วยังไม่พิสูจน์
Compile-readysource compile ใน target/build mode นั้นflow จริง, security, backend
Demo-readyผู้เรียนทดลอง deterministic flow ได้production identity และ operations
Production-readyrisk, platform, signing, data, observability และ release process ผ่านเกณฑ์ไม่มีคำอ้างแบบกว้าง ต้องมีหลักฐานรายระบบ
สถานะ Boilerplate ปัจจุบัน entrypoint ชื่อ main_production.dart ปิด diagnostic logging และ debug banner แต่ Authentication ยังใช้ fake datasource ดังนั้นเป็น production-minded composition example ไม่ใช่ production authentication

จัด workspace สำหรับการเรียน

โครงสร้างที่แนะนำ
Projects/
├── flutter-boilerplate/      # source ต้นฉบับ
├── my-task-app/              # clone ที่ใช้ลงมือทำ
└── flutter-document/         # คู่มือและ completed example

เก็บ working copy ของ Flutter นอก cloud-synced directory ถ้าเป็นไปได้ เพราะ build tools สร้างไฟล์จำนวนมากและระบบ sync อาจสร้าง conflict copy เช่น launch_background 2.xml ซึ่ง Gradle ไม่ยอมรับ

ความเข้าใจผิดที่พบบ่อย

  • “รู้ React แล้ว Flutter เหมือนกัน” — declarative คล้ายกัน แต่ runtime, layout และ state lifecycle ต่างกัน
  • “Hot reload ผ่านแปลว่าถูก” — hot reload ไม่ใช่ test และไม่จำลอง cold start
  • “Build ผ่านแปลว่าปล่อยได้” — build ไม่ตรวจ auth policy, privacy หรือ backend schema
  • “Clean Architecture ต้องมีทุก folder” — Boilerplate นี้เพิ่ม layer เมื่อมี responsibility เท่านั้น

Checkpoint ก่อนเดินต่อ

  1. อธิบายหัวข้อนี้ด้วยภาษาของตนเองโดยไม่เปิดคู่มือ
  2. ชี้ไฟล์หรือคำสั่งใน Boilerplate ที่สัมพันธ์กับบทนี้ได้
  3. รันตัวอย่างหรือ verification ที่บทกำหนดและอ่านผลลัพธ์ได้

Quiz ตรวจ mental model

สิ่งใดคือผลลัพธ์หลักของหลักสูตรนี้?

Practice

เขียนเป้าหมาย feature มือถือหนึ่งอย่าง แล้วระบุ Widget, state, data และ test ที่คาดว่าจะต้องมี

Definition of done: อธิบายเหตุผลของ design, แสดงผลลัพธ์ที่รันจริง และไม่มี warning ที่ถูกมองข้าม
