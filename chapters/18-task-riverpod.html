Capstone: Task State และ Filter ด้วย Riverpod

ประกอบ use cases, controller, loading/success/failure state และ derived filtered tasks

เวลาอ่าน 78 นาที ระดับ กลาง Task controller Riverpod filter Async state provider

เป้าหมายของบท

  • ออกแบบ TaskListState ที่ไม่มี contradictory state
  • โหลดและ mutate ผ่าน use case providers
  • สร้าง filtered view แบบ derived state
  • ทดสอบ controller ด้วย repository override

State shape

Invariant-preserving state
@freezed
sealed class TaskListState with _$TaskListState {
  const factory TaskListState.loading() = TaskListLoading;
  const factory TaskListState.ready({
    required List<Task> tasks,
    @Default(TaskFilter.all) TaskFilter filter,
    @Default(false) bool isMutating,
    String? actionError,
  }) = TaskListReady;
  const factory TaskListState.failed(Failure failure) = TaskListFailed;
}

loading ไม่มี stale error, failed ต้องมี Failure และ ready ต้องมี list แต่ mutation สามารถเกิดบน ready เพื่อยังแสดง content พร้อม disable action

Controller dependency

TaskListController
@Riverpod(keepAlive: true)
class TaskListController extends _$TaskListController {
  var _loadGeneration = 0;

  @override
  TaskListState build() {
    unawaited(Future<void>.microtask(load));
    return const TaskListState.loading();
  }

  Future<void> load() async {
    final current = state;
    if (current is TaskListReady && current.isMutating) return;

    final generation = ++_loadGeneration;
    state = const TaskListState.loading();
    final result = await ref.read(getTasksProvider).call();
    if (generation != _loadGeneration) return;
    state = switch (result) {
      Success(:final data) => TaskListState.ready(tasks: data),
      FailureResult(:final failure) => TaskListState.failed(failure),
    };
  }
}

Filter เป็น derived state

Visible tasks
extension TaskListReadyView on TaskListReady {
  List<Task> get visibleTasks {
    return tasks.where(filter.matches).toList(growable: false);
  }
}

ไม่ต้องเรียก repository ใหม่เมื่อเปลี่ยน filter เพราะ source list ไม่เปลี่ยน filter เป็น UI/application view state ที่ derive ได้ deterministic ระหว่าง mutation controller จะไม่รับ filter/reload ใหม่ และ UI disable controls เหล่านี้เพื่อไม่ให้ pre-await snapshot เขียนทับ state ที่ใหม่กว่า

Mutation transaction

Toggle
Future<void> toggle(String id) async {
  final current = state;
  if (current is! TaskListReady || current.isMutating) return;

  state = current.copyWith(isMutating: true);
  final result = await ref.read(toggleTaskProvider).call(id);

  state = switch (result) {
    Success<Task>(:final data) => current.copyWith(
        tasks: [
          for (final task in current.tasks)
            if (task.id == data.id) data else task,
        ],
        isMutating: false,
      ),
    FailureResult<Task>(:final failure) => current.copyWith(
        isMutating: false,
        actionError: failure.userMessage,
      ),
  };
}

ตัวอย่างใช้ confirmed update: รอ repository แล้ว mergeผลลง snapshot เดิม ระบบ latency สูงอาจเลือก optimistic update แต่ต้องออกแบบ rollback และ race condition เพิ่ม ไม่ควรทำเพียงเพื่อความรู้สึกเร็ว

Controller tests

  1. สร้าง completer repository เพื่อค้าง Future
  2. เรียก load แล้ว assert loading ก่อน complete
  3. complete ด้วย Success และ assert ready
  4. เปลี่ยน filter แล้ว assert visible tasks โดย repository call count ไม่เพิ่ม
  5. เรียก toggle ซ้ำระหว่าง isMutating แล้ว assert use case ถูกเรียกครั้งเดียว
  6. ค้าง mutation ด้วย Completer แล้ว assert filter/reload ถูก ignore
  7. ให้ load สองตัว complete สลับลำดับแล้ว assert generation ล่าสุดชนะ

Failure state กับ content preservation

ถ้า load ครั้งแรก fail หน้าเต็มเหมาะสม แต่ถ้า mutation บน list เดิม fail UX อาจควรรักษา list และเก็บ transient action failure แยกจาก load failure ให้ตัดสินตาม recovery ไม่ใช้ state เดียวกับทุก error โดยอัตโนมัติ

ข้อผิดพลาดที่พบบ่อย

  • เก็บทั้ง source tasks และ filtered tasks แล้วสองชุดไม่ sync
  • ใช้ bool loading/error/data nullable ร่วมกัน
  • ให้ Widget เรียก repository โดยตรง
  • ไม่ guard duplicate mutation
  • capture state ก่อน await แล้วเปิดให้ filter/reload เปลี่ยนระหว่างทาง
  • ทดสอบ mock call มากกว่าสถานะที่ consumer เห็น

Checkpoint ก่อนเดินต่อ

  1. อธิบายหัวข้อนี้ด้วยภาษาของตนเองโดยไม่เปิดคู่มือ
  2. ชี้ไฟล์หรือคำสั่งใน Boilerplate ที่สัมพันธ์กับบทนี้ได้
  3. รันตัวอย่างหรือ verification ที่บทกำหนดและอ่านผลลัพธ์ได้
