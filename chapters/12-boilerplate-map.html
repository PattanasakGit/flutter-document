12 · แผนที่ AI-first Flutter Boilerplate

D · Boilerplate Architecture · บทที่ 12

แผนที่ AI-first Flutter Boilerplate

อ่าน app, core, features, shared, tests, docs และ entrypoints จาก responsibility ไม่ใช่ชื่อ folder

เวลาอ่าน 55 นาที ระดับ กลาง feature-first app core shared AGENTS layers imports

เป้าหมายของบท

  • หา source จาก responsibility ได้เร็ว
  • เข้าใจ dependency direction ของแต่ละ layer
  • ใช้ nearest-home rule ก่อนสร้าง shared abstraction
  • อ่าน AGENTS.md เป็น executable team contract

Repository topology

Source map
lib/
├── app/                 # bootstrap, config, router, theme
├── core/                # errors, network, storage, result, logging
├── features/
│   ├── authentication/  # full vertical slice
│   ├── home/            # presentation-only example
│   └── tasks/           # capstone feature
├── shared/              # proven cross-feature code
└── main_*.dart          # environment entrypoints

test/                    # mirrors responsibility
docs/                    # architecture and team rules
scripts/                 # repeatable quality commands

Feature-first dependency graph

Request ไหล UI → application → repository แต่ dependency ของ Data ชี้เข้า Domain contract ทำให้ business code ไม่ import Dio หรือ secure storage plugin

เมื่อใดต้องมีแต่ละ layer

Layerสร้างเมื่อไม่ควรมี
Presentationfeature มี UI/state interactionDio, DTO, plugin exception
Applicationworkflow มี orchestration/validation ที่ใช้ซ้ำBuildContext, Widget
Domainมี entity/rule/contractFlutter/plugin/import Data
Dataมี API/storage/platform boundaryUI state และ Widget

Nearest-home rule

  1. เริ่มไฟล์ใหม่ใน feature ที่ใช้
  2. ถ้าใช้ซ้ำภายใน feature ให้วางระดับ feature
  3. เมื่อ feature ที่สองต้องใช้ ให้ประเมิน abstraction จากสอง use cases จริง
  4. ย้ายไป shared/core เฉพาะ business-neutral responsibility

การสร้าง shared ก่อนมีผู้ใช้จริงทำให้ API ออกแบบจากการเดาและ AI มีโอกาส เลือก abstraction กว้างเกิน scope

Core กับ Shared ต่างกัน

  • Core: infrastructure กลาง เช่น ApiClient, Result, logger, storage wrapper
  • Shared: UI/validator ที่พิสูจน์ว่าใช้ข้าม feature
  • Feature public surface: export เฉพาะสิ่งที่ feature อื่นจำเป็นต้องรู้

AGENTS.md สำหรับ Dev และ AI

อ่านก่อนแก้ source เพราะระบุ import boundary, error flow, naming, testing, environment และข้อห้ามเรื่อง secrets Dev ใช้เป็น review checklist ส่วน AI ใช้ลด ambiguity ก่อน generate code

Decision flow ก่อนเพิ่ม feature

คำถามตามลำดับ
1. User-visible responsibility คืออะไร?
2. Presentation อย่างเดียวพอหรือมี business rule?
3. มี external I/O หรือไม่?
4. Contract ควรอยู่ Domain หรือ Core?
5. State owner และ lifetime คืออะไร?
6. Test ต่ำสุดที่พิสูจน์ behavior คือระดับใด?
7. Public surface ที่ feature อื่นต้องใช้มีอะไร?

ข้อผิดพลาดที่พบบ่อย

  • สร้าง global folders เช่น screens/services/models แล้ว feature กระจายทั้ง repo
  • บังคับทุก feature มี 4 layers แม้เป็น static page
  • ให้ Presentation import DTO เพราะสะดวก
  • export internal controller/model ทุกไฟล์จาก barrel
  • กฎอยู่แต่ในเอกสารโดยไม่ให้ test/analyzer/CI ช่วย enforce

Checkpoint ก่อนเดินต่อ

  1. อธิบายหัวข้อนี้ด้วยภาษาของตนเองโดยไม่เปิดคู่มือ
  2. ชี้ไฟล์หรือคำสั่งใน Boilerplate ที่สัมพันธ์กับบทนี้ได้
  3. รันตัวอย่างหรือ verification ที่บทกำหนดและอ่านผลลัพธ์ได้
