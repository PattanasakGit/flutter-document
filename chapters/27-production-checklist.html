27 · Production Readiness และ Next-system Checklist

Production Readiness และ Next-system Checklist

ประเมิน auth, API, data, test, CI, release, privacy และ operations ก่อนส่งระบบจริง

เวลาอ่าน 58 นาที ระดับ กลาง production readiness checklist CI release privacy observability

เป้าหมายของบท

  • ใช้ checklist เป็น risk review ที่มี owner/evidence ไม่ใช่พิธีการ
  • แบ่ง Compile-ready, Demo-ready, Release-ready และ Operable
  • จัดลำดับ P0/P1/P2 จาก impact และ likelihood
  • กำหนด go/no-go และ rollback criteria ก่อนเปิดระบบ

ระดับความพร้อม

ระดับพิสูจน์แล้วยังไม่ควรอ้าง
Compile-readysource สร้าง artifact ได้flow ถูกต้อง/ปลอดภัย
Demo-readyhappy path สาธิตได้ใน environment ควบคุมreal auth/data/scale
Release-readyrequirements, security, test, signing, store ผ่านดูแลได้หลังปล่อย
Operablemonitor, alert, incident, rollback, ownership พร้อมไม่มีความเสี่ยงเลย

Scoring ที่ใช้ตัดสินใจได้

Risk score
risk = impact (1–5) × likelihood (1–5)

20–25  → P0: ปิดก่อน release
12–19  → P1: owner + deadline + mitigation
 6–11  → P2: track ใน backlog
 1–5   → accept พร้อมเหตุผล

คะแนนเป็นเครื่องช่วยสนทนา ไม่แทน judgment เช่น data leak อาจเป็น P0 แม้ likelihood ต่ำ เพราะผลกระทบและข้อกำกับสูง

Product และ UX

  • Acceptance criteria ของ critical flow ผ่านบน device matrix
  • empty/loading/error/offline/permission-denied state มีข้อความและทางไปต่อ
  • double tap, retry และ background/foreground ไม่สร้างข้อมูลซ้ำ
  • accessibility: semantics, contrast, keyboard, text scale ผ่าน
  • localization, timezone, locale number/date และข้อความยาวผ่าน

Architecture และ data

  • dependency direction ตรงกับ architecture contract
  • domain ไม่อ้าง DTO/plugin/platform type
  • migration ถูกทดสอบจาก production version ก่อนหน้า
  • offline/sync/conflict/idempotency policy ถูกเขียนและทดสอบ
  • cache invalidation, retention และ user-scoped cleanup ชัดเจน

Security และ privacy

  • threat model ครอบคลุม auth, storage, network และ deep links
  • ไม่มี secret ใน source, artifact, logs หรือ analytics
  • token restore/refresh/revoke/race condition ถูกทดสอบ
  • dependency/security scan ผ่านและ exception มี owner/expiry
  • privacy disclosure, consent, export/delete และ retention ตรงระบบจริง

Quality gate

  • format, analyze, unit/widget/router/integration tests ผ่านจาก clean checkout
  • critical failure paths และ unknown route ถูกทดสอบ
  • performance baseline บนอุปกรณ์ขั้นต่ำไม่มี P0 regression
  • crash-free baseline และ error budget ถูกกำหนด
  • artifact ตรง commit/tag ที่ approve และมี checksum

Delivery และ stores

  • application/bundle id, version, icons, metadata และ screenshots ถูก environment
  • signing certificate/profile/keystore rotation และ backup มี owner
  • native permissions/capabilities/privacy manifests ครบ
  • staged rollout, kill switch และ rollback procedure ถูกซ้อม
  • support channel และ release communication พร้อม

Operations

  • dashboard ครอบคลุม crash, latency, API error, auth failure และ critical outcome
  • alert มี threshold, owner, escalation และ runbook
  • log/trace มี correlation id และ redact ข้อมูลอ่อนไหว
  • backend/mobile compatibility window และ forced-upgrade policy ชัดเจน
  • incident review สร้าง action ที่มี owner/deadline

ประเมินแอป Task ตัวอย่าง

GapRiskPriorityAcceptance criteria
Demo authenticationไม่มี real identity/session securityP0OIDC/backend flow + restore/refresh/revoke tests
In-memory tasksข้อมูลหายเมื่อปิดแอปP0persist/sync + migration/conflict tests
No production telemetryไม่เห็น incident หลัง releaseP0redacted crash/error/performance telemetry + alerts
No store signingแจก artifact ไม่ได้P1protected CI signing + staged internal release
Limited locale setUX ไม่ครบตลาดเป้าหมายP2approved locale matrix + QA

Go / No-go meeting

ถ้ามี P0 เปิดอยู่ให้เป็น no-go เว้นแต่ผู้มีอำนาจยอมรับความเสี่ยงอย่างชัดเจน พร้อม mitigation และเวลาปิดที่ตรวจสอบได้

จากตัวอย่างสู่ระบบถัดไป

  1. คง feature boundaries และ typed failures ที่พิสูจน์แล้ว
  2. แทน in-memory datasource ด้วย boundary ที่ต้องการ ไม่ rewrite presentation
  3. ทำ auth/session และ observability ก่อนเพิ่ม feature จำนวนมาก
  4. เพิ่ม CI gate และ release rehearsal ตั้งแต่ milestone แรก
  5. ทบทวน architecture decision เมื่อ assumption เปลี่ยน ไม่ตาม calendar อย่างเดียว

ข้อผิดพลาดที่พบบ่อย

  • ติ๊ก checklist โดยไม่มีลิงก์ evidence
  • ทุก risk เป็น P0 จนไม่มีลำดับ
  • release ก่อนกำหนด rollback threshold
  • ให้ทีม mobile รับผิดชอบ backend/store/operations โดยไม่มี owner ร่วม
  • ถือว่า “ไม่มี bug ที่รู้จัก” เท่ากับพร้อม production

Checkpoint ก่อนเดินต่อ

  1. อธิบายหัวข้อนี้ด้วยภาษาของตนเองโดยไม่เปิดคู่มือ
  2. ชี้ไฟล์หรือคำสั่งใน Boilerplate ที่สัมพันธ์กับบทนี้ได้
  3. รันตัวอย่างหรือ verification ที่บทกำหนดและอ่านผลลัพธ์ได้
