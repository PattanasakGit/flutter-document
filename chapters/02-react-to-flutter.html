02 · แผนที่ความคิดจาก React และ Next.js สู่ Flutter

A · Orientation & Setup · บทที่ 02

แผนที่ความคิดจาก React และ Next.js สู่ Flutter

ใช้ความรู้เดิมเป็นสะพาน แต่แยก DOM, Widget, runtime และ state ownership ให้ถูกต้อง

เวลาอ่าน 28 นาที ระดับ เริ่มต้น React Next.js JSX DOM Widget hooks provider

เป้าหมายของบท

  • จับคู่ concept ที่คุ้นเคยโดยไม่คิดว่า implementation เท่ากัน
  • เข้าใจความต่างระหว่าง Browser DOM กับ Flutter rendering pipeline
  • เลือก owner ของ UI, state, navigation และ data ได้ถูก layer

Concept map หลัก

React / Next.jsFlutterข้อแตกต่างสำคัญ
JSX elementWidgetWidget เป็น immutable configuration ไม่ใช่ DOM node
Component instanceElementElement รักษาตำแหน่งและ lifecycle ใน tree
Browser layout/paintRenderObjectFlutter คุม constraints, layout และ paint pipeline
propsconstructor parametersDart ใช้ named/required parameters และ nominal types
useStateStatefulWidget/setStateเหมาะกับ state ที่ widget เป็นเจ้าของและอายุสั้น
Context/Zustand/ReduxRiverpodRiverpod เป็นทั้ง state graph และ dependency composition
React Router/App RouterGoRoutermobile back stack และ deep link ต้องคิดร่วมกัน
fetch/axiosDioDio ควรอยู่ data boundary ไม่ไหลถึง UI
localStorageplatform storage abstractionsecure data ต้องใช้ Keychain/Keystore และ config ราย platform
npm testflutter testWidget test รัน Flutter binding โดยไม่ต้องเปิด simulator
Analogy มีวันหมดอายุ ใช้ตารางนี้เพื่อถามว่า “responsibility นี้อยู่ตรงไหน” ไม่ใช่เพื่อย้าย pattern จาก Web แบบคำต่อคำ ตัวอย่างเช่น อย่าหา useEffect ทุกครั้งที่ Widget สร้าง เพราะ lifecycle และ provider ownership ให้ทางเลือกที่แม่นกว่า

สาม tree แทน DOM mental model

เมื่อ parent build ใหม่ Flutter เปรียบเทียบ Widget configuration กับ Element เดิม แล้วอัปเดต RenderObject เฉพาะส่วนที่จำเป็น ไม่ได้ลบและสร้าง pixel ทุกครั้ง

จาก React component ไป Widget

React
type TaskCardProps = {
  title: string;
  completed: boolean;
  onToggle(): void;
};

export function TaskCard(props: TaskCardProps) {
  return (
    <button onClick={props.onToggle}>
      {props.completed ? "Done" : "Open"} · {props.title}
    </button>
  );
}
Flutter
final class TaskCard extends StatelessWidget {
  const TaskCard({
    required this.title,
    required this.completed,
    required this.onToggle,
    super.key,
  });

  final String title;
  final bool completed;
  final VoidCallback onToggle;

  @override
  Widget build(BuildContext context) {
    return FilledButton.tonal(
      onPressed: onToggle,
      child: Text('${completed ? 'Done' : 'Open'} · $title'),
    );
  }
}

ทั้งสองตัวอย่าง declarative และรับ data/callback จากภายนอก แต่ Flutter constructor ทำหน้าที่เป็น typed props contract, key ช่วย identity ใน Element tree และปุ่มมี Material semantics/interaction จาก framework

เลือก state owner จากอายุและขอบเขต

StateOwner ที่เหมาะเหตุผล
Password visibilityLogin form widgetใช้หน้าเดียว อายุสั้น ไม่ต้อง persist
Task filterTask controller/providerเป็นส่วนของ feature state และต้อง test
Authenticated sessionSession provider/repositoryหลาย route ใช้และต้อง restore
Text field draftForm controllerผูก focus/validation กับ form lifecycle

Data fetching ไม่ควรจบที่ Dio

ความต่างของ responsibility
// Web component ที่เล็กอาจ fetch โดยตรงได้
const response = await fetch('/api/tasks');

// Boilerplate แยก boundary
TaskPage
  → TaskListController
  → GetTasks
  → TaskRepository
  → TaskRemoteDatasource
  → Dio

การแยกนี้ไม่ได้ทำเพราะ Flutter บังคับ แต่ทำเพื่อป้องกัน HTTP shape, DioException และ plugin detail ไหลเข้ามาใน business/UI code

ความผิดพลาดจากการย้าย mental model

  • สร้าง service locator global เพราะคิดว่าเหมือน import singleton ใน JavaScript
  • ใช้ BuildContext หลัง await โดยไม่ตรวจ mounted
  • ห่อทุกอย่างด้วย Riverpod ทั้งที่ state มี owner แค่ widget เดียว
  • ใช้ fixed width แบบ CSS desktop จน constraints บนมือถือ overflow
  • เรียก API ใน build ทำให้ request ซ้ำทุก rebuild

Checkpoint ก่อนเดินต่อ

  1. อธิบายหัวข้อนี้ด้วยภาษาของตนเองโดยไม่เปิดคู่มือ
  2. ชี้ไฟล์หรือคำสั่งใน Boilerplate ที่สัมพันธ์กับบทนี้ได้
  3. รันตัวอย่างหรือ verification ที่บทกำหนดและอ่านผลลัพธ์ได้
