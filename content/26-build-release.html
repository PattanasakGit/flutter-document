  • เข้าใจ debug, profile และ release mode ว่าพิสูจน์คนละเรื่อง
  • สร้าง Android, iOS และ Web artifact พร้อมระบุ output และข้อกำหนด

  • สร้าง release verification และ rollback evidence ที่ทำซ้ำได้

Build modes

Modeใช้เมื่อลักษณะสำคัญ
debugพัฒนาและ hot reloadassert/debug service เปิด, performance ไม่แทนผู้ใช้จริง
profileวัด performance บนอุปกรณ์instrumentation สำหรับ profiling, ใกล้ release
releaseแจกจ่ายoptimization เปิด, debug service ปิด, ต้องใช้ signing/config จริง

Android: APK และ App Bundle

Local verification และ store artifact
# ติดตั้ง/แจกภายในแบบไฟล์เดียว
flutter build apk \
  --release \
  --dart-define=APP_ENV=production

# Play Store
flutter build appbundle \
  --release \
  --dart-define=APP_ENV=production
  • APK โดยทั่วไปอยู่ใต้ build/app/outputs/flutter-apk/
  • AAB อยู่ใต้ build/app/outputs/bundle/release/
  • ตั้ง applicationId, versionCode/versionName และ signing config ให้ถูก environment
  • เก็บ keystore/password ใน protected secret ไม่ commit
  • ทดสอบ release artifact บนอุปกรณ์จริงและ Android version ขั้นต่ำ/เป้าหมาย

iOS: archive และ IPA

ต้องใช้ macOS + Xcode
flutter build ios \
  --release \
  --dart-define=APP_ENV=production

flutter build ipa \
  --release \
  --dart-define=APP_ENV=production
  • ตรวจ Bundle Identifier, Team, certificate และ provisioning profile
  • เปิด workspace ไม่ใช่ project เมื่อ CocoaPods สร้าง workspace
  • ตรวจ deployment target, privacy usage descriptions และ capabilities
  • upload ผ่าน Xcode/Transporter/CI แล้วตรวจ processing warning
  • Windows/Linux build iOS ไม่ได้ ต้องใช้ macOS build agent

Web release

Build และ serve แบบ static
flutter build web \
  --release \
  --dart-define=APP_ENV=production

python3 -m http.server 8080 --directory build/web

ทดสอบผ่าน HTTP server ไม่เปิด index.html ตรง ๆ และตั้ง hosting fallback ไป index.html สำหรับ path-based navigation ตรวจ CORS, base href, cache headers และ service-worker update policy

Versioning

pubspec.yaml
version: 1.4.0+27
#         │ │ │  └─ build number / versionCode
#         └─┴─┴──── semantic version shown to users

กำหนด source of truth หนึ่งที่และให้ CI เพิ่ม build number แบบ monotonic release note ต้องผูก version, commit และ migration ที่เกี่ยวข้อง

ตัวอย่าง release pipeline

Artifact ที่ผ่าน QA ต้องเป็นไฟล์เดียวกับที่แจกจริง ไม่ rebuild หลัง approve เพราะ dependency, signing หรือ environment อาจต่างกัน

Post-build verification

  1. บันทึก checksum และขนาด artifact
  2. ติดตั้ง artifact release บนอุปกรณ์ clean state
  3. ทดสอบ cold start, upgrade จาก version ก่อน, login/restore และ critical flow
  4. ตรวจ network ชี้ endpoint ถูก environment และไม่มี verbose secret log
  5. ตรวจ crash reporting symbolication และ release tag
  6. ซ้อม rollback/disable feature ที่เสี่ยงก่อน rollout กว้าง

ข้อผิดพลาดที่พบบ่อย

  • ส่ง debug APK ให้ผู้ใช้จริง
  • ทดสอบ source หนึ่ง commit แต่ build อีก commit
  • เก็บ signing password ใน repository
  • build web ผ่านแล้วไม่ทดสอบ deep-link refresh
  • ถือว่า compile success พิสูจน์ auth, API, privacy และ operations แล้ว
