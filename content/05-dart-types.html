เป้าหมายของบท

  • อ่าน entrypoint และ declaration ของ Dart ได้
  • ใช้ type inference โดยไม่ทำให้ public API คลุมเครือ
  • แยก final, const และ mutable variable
  • ใช้ named parameter, enum, record และ switch expression
จาก TypeScript Dart เป็น statically typed แบบ nominal เป็นหลัก class/interface identity มีความหมาย ไม่ใช่ structural typing แบบ TypeScript ที่ object shape ตรงกัน แล้ว assign ได้เสมอ

โครงสร้างโปรแกรมและ main

Dart
import 'package:flutter/material.dart';

void main() {
  runApp(const App());
}

ทุก Dart application เริ่มจาก top-level main ซึ่งคืน void หรือ Future<void> ได้ ใน Boilerplate entrypoint เรียก shared bootstrap พร้อม environment config ต่างกัน

varlet พร้อม inferred typeDart ไม่เปลี่ยน type ภายหลัง

Named และ required parameters

Dart API design
Task createTask({
  required String title,
  String description = '',
  DateTime? dueAt,
}) {
  return Task(
    id: 'generated-id',
    title: title.trim(),
    description: description.trim(),
    dueAt: dueAt,
  );
}

final task = createTask(
  title: 'Learn Dart',
  dueAt: DateTime(2026, 8, 1),
);

Named parameter ทำให้ call site อ่านความหมายได้และลด bug จาก parameter ที่ type เหมือนกันหลายตัว ใช้ required เมื่อ null/default ไม่ใช่ state ที่ถูกต้อง

Enum และ Record

Dart 3
enum TaskFilter { all, open, completed }

typedef TaskSummary = ({
  int total,
  int open,
  int completed,
});

TaskSummary summarize(List<Task> tasks) {
  final completed = tasks.where((task) => task.isCompleted).length;
  return (
    total: tasks.length,
    open: tasks.length - completed,
    completed: completed,
  );
}

final (:total, :open, :completed) = summarize(tasks);

Record เหมาะกับค่าชั่วคราวหลายช่องที่ไม่มี domain identity ถ้าค่านั้นมี behavior, invariant หรือใช้ข้าม boundary ให้สร้าง named class แทน

Exhaustive switch expression

Dart
String filterLabel(TaskFilter filter) => switch (filter) {
  TaskFilter.all => 'ทั้งหมด',
  TaskFilter.open => 'ยังไม่เสร็จ',
  TaskFilter.completed => 'เสร็จแล้ว',
};

เมื่อเพิ่ม enum value ใหม่ analyzer บังคับให้จัดการครบ ต่างจาก default กว้าง ๆ ที่อาจซ่อน state ใหม่

Type ที่ boundary

ภายใน function สั้นใช้ inference ได้ แต่ public fields, return type, repository contract และ provider ควรบอก type ชัดเพื่อเป็น API ให้คนและ AI

ชัดเจนกว่า dynamic
abstract interface class TaskRepository {
  Future<Result<List<Task>>> getTasks();
}

// หลีกเลี่ยง
Future getTasks() async => fetchSomething();

ข้อผิดพลาดที่พบบ่อย

  • ใช้ dynamic เพื่อให้ analyzer เงียบ แล้วเลื่อน error ไป runtime
  • ใช้ var ใน public field จนคนอ่านไม่รู้ contract
  • คิดว่า final List ทำให้สมาชิก list immutable
  • ใช้ positional parameter หลายตัวที่เป็น String เหมือนกัน
  • สร้าง class สำหรับค่าชั่วคราวทุกคู่ ทั้งที่ Record สื่อ intent ได้พอ
