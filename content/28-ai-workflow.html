เป้าหมายของบท

  • ใช้ AI สำรวจ วางแผน implement review และ verify โดยรักษาขอบเขต
  • เขียน prompt ที่บอก behavior, architecture contract และหลักฐานที่ต้องส่ง
  • แบ่งงานให้มี context พอดีและตรวจ diff ได้
  • ป้องกัน hallucinated API, dependency drift, secret leakage และ scope creep

AI working contract

AI ช่วยเร่ง feedback loop แต่ไม่ได้แทน product decision, security ownership หรือหลักฐานจาก compiler/test/runtime ผู้พัฒนายังคงรับผิดชอบสิ่งที่ merge

หลักสำคัญ: Context ที่ชัด + scope ที่เล็ก + acceptance criteria ที่รันได้ ให้ผลดีกว่า prompt ยาวที่ขอ “ทำแอปทั้งหมดให้ดีที่สุด”

AI-assisted development loop

ถ้าพบ unexpected failure ให้กลับไป Explore/Observe ไม่ให้ AI เดา patch ต่อเนื่องจน tests บังเอิญผ่านโดยไม่เข้าใจ root cause

Context pack ที่ AI ต้องรู้

ข้อมูลตัวอย่างเหตุผล
Goalเพิ่ม task priorityกำหนด outcome
Scopefeatures/tasks เท่านั้นหยุด scope creep
ContractDomain ห้าม import Flutter/DTOรักษา dependency direction
Nearby patternsใช้ Result/Failure และ Riverpod codegen เดิมไม่สร้าง abstraction ซ้ำ
Behaviorเรียง high → normal → low แบบ stabletest ได้
Constraintsไม่เพิ่ม package, offline testsจำกัดทางเลือก
Verificationfocused tests, analyze, full testสร้าง evidence

Prompt template สำหรับ feature

คัดลอกแล้วแทนค่าที่อยู่ใน [ ]
Goal:
เพิ่ม [behavior] ใน [feature]

Read first:
- AGENTS.md ที่เกี่ยวข้องทั้งหมด
- [nearby implementation files]
- [nearby tests]
- pubspec.yaml / lockfile สำหรับ API version

Architecture constraints:
- รักษา Domain → Application ← Data/Presentation
- ใช้ Result/Failure และ provider pattern ที่มีอยู่
- ห้ามเพิ่ม dependency หรือแก้ public API นอก scope โดยไม่รายงาน

Behavior / edge cases:
- [given / when / then]
- [failure / empty / concurrent action]

Workflow:
1. สรุป current pattern และแผนไฟล์
2. เขียน failing tests และแสดง failure ที่คาด
3. implement เล็กที่สุดให้ผ่าน
4. review diff เรื่อง types, null, async race, UX, security
5. รัน format, analyze, focused tests และ full tests

Deliver:
- changed files
- decisions/tradeoffs
- exact verification results
- remaining production gaps

ตัวอย่าง prompt: เพิ่ม Priority

พร้อมใช้กับ Boilerplate นี้
เพิ่ม TaskPriority {high, normal, low} ใน features/tasks

Behavior:
- task ใหม่ default เป็น normal
- filter เดิมยังทำงาน
- list เรียง high → normal → low และรักษาลำดับเดิมภายใน priority
- form ต้องเลือก priority ด้วย accessible control
- DTO unknown value map เป็น normal และบันทึก warning แบบไม่ใส่ payload

อย่าแก้ auth, core network หรือเพิ่ม package
เริ่มจาก domain/data/controller/widget failing tests
รัน build_runner เฉพาะเมื่อ annotation เปลี่ยน
รายงาน focused/full test และ flutter analyze ตาม output จริง

แบ่งงานให้ AI ตรวจง่าย

  1. Domain contract + unit tests
  2. Datasource/repository mapping + tests
  3. Controller state transition + tests
  4. Presentation behavior + widget tests
  5. Router/integration wiring
  6. Docs, changelog และ release evidence

แต่ละชิ้นควรมี working state และ commit ที่อธิบายได้ อย่าให้ AI เปลี่ยน architecture, package versions, generated code และ UI ทั้งระบบใน diff เดียว

Human review checklist

  • โค้ดตอบ behavior ที่ขอจริงหรือเพียงทำ test ที่ AI เขียนเองผ่าน
  • API มีอยู่ใน dependency version ปัจจุบันหรือ hallucinate
  • import direction และ public surface ยังถูกต้อง
  • null/async/cancellation/concurrent action มี race หรือไม่
  • error ถูกแปลงและผู้ใช้มี recovery action หรือไม่
  • log/test fixture/diff มี secret หรือ personal data หรือไม่
  • generated file มาจาก command และไม่มี unrelated change
  • verification output ใหม่และตรง commit ปัจจุบันหรือไม่

ส่ง context ให้ AI อย่างปลอดภัย

  • ใช้ sanitized fixture แทน production payload
  • ไม่ paste token, key, cookie, customer log หรือ crash dump ที่ยังไม่ redact
  • บอก AI ไม่ให้เปิด/ส่งไฟล์ env, keychain, provisioning หรือ secret store
  • จำกัด file scope และตรวจ git diff ก่อน commit
  • ใช้ dependency source/docs ปัจจุบันเมื่อต้องยืนยัน API ที่เปลี่ยนตาม version

เมื่อ test fail ให้ prompt แบบ diagnosis

ไม่สั่ง “แก้ให้ผ่าน” อย่างเดียว
นี่คือ command และ output เต็มจาก focused test: [output]

ก่อนแก้:
1. reproduce ด้วย command เดิม
2. แยก expected behavior จาก observed behavior
3. trace state/data จาก boundary ที่ใกล้ที่สุด
4. เสนอ hypothesis ที่พิสูจน์ได้ พร้อมไฟล์/บรรทัด
5. เขียนหรือปรับ regression test ให้ fail เพราะ root cause

แก้เฉพาะเมื่อมีหลักฐาน แล้วรัน focused + related + full suite
ห้ามล้าง cache/upgrade dependency เว้นแต่พิสูจน์ว่าเป็นสาเหตุ

Definition of done สำหรับงานที่ AI ช่วย

  • Acceptance criteria ถูกแปลงเป็น tests หรือ verification steps
  • diff อยู่ใน scope และ architecture contract ผ่าน
  • format, analyze, focused/full tests มี output จริง
  • manual flow ที่ automation ไม่ครอบคลุมถูกตรวจ
  • docs/decision/production gaps ถูกปรับ
  • ผู้พัฒนาอธิบาย code path และ rollback ได้โดยไม่พึ่ง transcript

ข้อผิดพลาดที่พบบ่อย

  • ให้ AI เดา requirement ที่เป็น product/security decision
  • รับ API หรือ package name โดยไม่ตรวจ version/source
  • ขอ refactor ใหญ่พร้อม feature และ bug fix ในครั้งเดียว
  • เชื่อข้อความ “tests pass” โดยไม่มี command output ใหม่
  • ส่ง production secret/log จริงเพื่อให้ debug เร็วขึ้น
