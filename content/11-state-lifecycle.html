เป้าหมายของบท

  • เลือก state owner จาก scope และ lifetime
  • ใช้ StatefulWidget สำหรับ local ephemeral state
  • ใช้ Riverpod สำหรับ shared/testable application state
  • หลีกเลี่ยง invalid state combination

ถามห้าอย่างก่อนเลือกเครื่องมือ

  1. Owner: ใครมีสิทธิ์เปลี่ยน state?
  2. Consumers: Widget/route กี่ตัวอ่าน?
  3. Lifetime: อยู่แค่ frame, page, session หรือข้าม restart?
  4. Boundary: ต้องเรียก repository/plugin หรือไม่?
  5. Testability: business transition ต้อง test แยก UI หรือไม่?

setState ที่ถูกขอบเขต

Ephemeral state
var _selectedTab = 0;

void _selectTab(int value) {
  if (_selectedTab == value) return;
  setState(() => _selectedTab = value);
}

setState ไม่ได้ “set ค่าใน framework” แต่แจ้ง Element ว่า state เปลี่ยนและ subtree ควร build ใหม่ เก็บ mutation ให้อยู่ใน callback สั้นและ ไม่ทำ async work ภายใน setState

Controller สำหรับ application transition

State transition
Future<void> load() async {
  state = const TaskLoading();
  final result = await _getTasks();
  state = switch (result) {
    Success(:final data) => TaskReady(tasks: data),
    FailureResult(:final failure) => TaskFailed(failure: failure),
  };
}

Controller รู้ use case และเปลี่ยน state แต่ไม่สร้าง Dialog/Snackbar ด้วย BuildContext Presentation watch state แล้วแสดงผลตาม state

ออกแบบ state ให้ผิดยาก

หลีกเลี่ยง nullable combination
// สร้าง loading + error + data พร้อมกันได้
class WeakState {
  bool loading;
  List<Task>? tasks;
  Failure? error;
}

// แต่ละ subtype มีข้อมูลที่จำเป็นเท่านั้น
sealed class TaskState {}
final class TaskLoading extends TaskState {}
final class TaskReady extends TaskState {
  TaskReady(this.tasks);
  final List<Task> tasks;
}
final class TaskFailed extends TaskState {
  TaskFailed(this.failure);
  final Failure failure;
}

Lifecycle ที่ต้องนึกถึง

  • initState: subscribe/create สิ่งที่ใช้ตลอด State lifetime
  • didChangeDependencies: dependency จาก context เปลี่ยน
  • didUpdateWidget: parent ส่ง configuration ใหม่
  • dispose: cancel subscription/dispose controller
  • Provider autoDispose: release state เมื่อไม่มี listener ตาม policy

Side effect อยู่ที่ไหน

UI event เรียก controller, controller เรียก use case, use case/repository ทำ external work ผ่าน abstraction ส่วน Snackbar/navigation เป็น presentation reaction ที่ใช้ ref.listen หรือ event result อย่างระมัดระวัง

ข้อผิดพลาดที่พบบ่อย

  • ย้ายทุก boolean ไป global provider แม้ widget เดียวใช้
  • เก็บ BuildContext ใน controller
  • เริ่ม async load ซ้ำทุก build
  • ใช้ enum + nullable payload จนมี invalid combination
  • ลืม session initialization state ทำให้ router redirect เร็วเกินไป
