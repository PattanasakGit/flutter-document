Architecture Decision Matrix

ตารางตัดสินใจเลือก layer, state owner, repository, storage, routing และ test level

เวลาอ่าน 30 นาที ระดับ อ้างอิง decision matrix layer state repository storage routing

วิธีใช้ Decision Matrix

เริ่มจาก responsibility, owner, lifetime, boundary และ risk แล้วเลือก pattern ที่เล็กที่สุดซึ่งรักษา testability ได้ ตารางนี้เป็น decision aid ไม่ใช่กฎว่าทุก feature ต้องมีทุก layer

Repository และ datasource

  • มี repository เมื่อ domain/application ต้องการ contract ที่ไม่ผูก transport
  • มี datasource เมื่อ repository ต้องคุย external mechanism หรือสลับ implementation
  • ไม่ต้องสร้าง interface ทุก class; สร้างตรง boundary ที่ต้อง fake/replace
  • DTO อยู่ data layer และ map ก่อนออกจาก boundary
  • Repository คืน domain value/typed failure ไม่คืน Dio response หรือ plugin exception

เมื่อใดควรย้ายไป shared/core

  1. มี consumer ข้าม feature อย่างน้อยสองแห่งที่ใช้ contract เดียวกันจริง
  2. ชื่อ abstraction มาจาก responsibility ไม่ใช่การลบ duplication ผิวเผิน
  3. API stable พอและ dependency direction ไม่กลับหัว
  4. มี tests/owner และการเปลี่ยนไม่ทำให้ทุก feature lock-step โดยไม่จำเป็น

ตัวอย่าง: Notification settings

Decision record สั้น
Responsibility: ผู้ใช้ตั้งค่า reminder ต่อประเภท task
Owner/lifetime: feature state + persisted per user
Domain: NotificationPreference, schedule invariant
Application: SettingsController
Data: SettingsRepositoryImpl + local/remote datasource
Presentation: SettingsPage
Core reuse: NotificationScheduler adapter เมื่อ feature อื่นใช้จริง
Test: domain timezone rules, repository mapping, controller save failure,
      widget semantics, platform integration smoke

คำถามก่อนสร้าง abstraction

  • ถ้า backend เปลี่ยน transport Domain ต้องแก้หรือไม่?
  • ถ้า UI เปลี่ยน Repository ต้องแก้หรือไม่?
  • ทดสอบ business rule โดยไม่เปิด Flutter binding ได้หรือไม่?
  • แทน external dependency ด้วย fake ที่ boundary เดียวได้หรือไม่?
  • คนใหม่หา nearest home ของไฟล์นี้จาก responsibility ได้หรือไม่?

ข้อผิดพลาดที่พบบ่อย

  • เลือก architecture จากชื่อ package ก่อนรู้ requirement
  • สร้าง Core/Shared เป็นถังรวม miscellaneous
  • ทำ repository ที่เพียง forward ทุก method โดยไม่มี boundary value
  • เก็บ UI controller ใน global provider ทั้งที่มี owner เป็น widget
  • เพิ่ม layer แล้วไม่มี test หรือการสลับ implementation ใดได้ประโยชน์

Checkpoint ก่อนเดินต่อ

  1. อธิบายหัวข้อนี้ด้วยภาษาของตนเองโดยไม่เปิดคู่มือ
  2. ชี้ไฟล์หรือคำสั่งใน Boilerplate ที่สัมพันธ์กับบทนี้ได้
  3. รันตัวอย่างหรือ verification ที่บทกำหนดและอ่านผลลัพธ์ได้
